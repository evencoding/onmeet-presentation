# OnMeet Backend 개발 회고

> 프로젝트 기간 중 마주한 아키텍처 설계, 기술적 선택, 장애 대응, 그리고 아직 풀지 못한 숙제들을 기록합니다.
> 담당 파트: MSA 설계, auth-service, gateway-service, email-service, file-service, onmeet-common, common-security, Nginx, 인프라/CI/CD

---

## 1. MSA 설계 — "왜 모놀리스가 아닌가"

OnMeet은 화상회의, AI 요약, 실시간 알림, 파일 관리 등 도메인이 명확하게 분리되는 서비스다. 초기에 모놀리식으로 시작했지만, 1주차에 MSA로 전환하는 결정을 내렸다.

### 전환 계기

모놀리식 구조에서 video-service의 LiveKit 의존성이 auth-service의 빌드를 느리게 만들고, ai-service의 무거운 STT 처리가 나머지 서비스의 응답 시간에 영향을 주는 상황이 벌어졌다. "이 서비스들은 독립적으로 배포되어야 한다"는 판단이 들었다.

### 서비스 분리 기준

| 서비스 | 기술 스택 | 분리 이유 |
|--------|----------|----------|
| auth-service | Kotlin | 인증은 모든 서비스의 진입점, 독립적 스케일링 필요 |
| gateway-service | Kotlin/WebFlux | 리액티브 모델이 필요, 다른 서비스와 스레딩 모델 다름 |
| video-service | Java | LiveKit/WebRTC 의존성 격리, 무거운 미디어 처리 |
| ai-service | Java | GPU/CPU 집약적 STT, 독립적 리소스 할당 필요 |
| notification-service | Java | SSE long-lived 커넥션, 다른 서비스와 커넥션 모델 다름 |
| file-service | **Go** | 성능 극대화를 위해 기술 스택 자체를 전환 |
| email-service | Java | 외부 SMTP 의존, 장애 격리 필요 |

**결론**: MSA의 진짜 장점은 "서비스별로 최적의 기술을 선택할 수 있다"는 것이었다. file-service를 Java에서 Go로 전환한 것이 대표적인 사례다.

## 2. 인증 아키텍처 — "비밀키를 공유하지 않는 분산 인증"

MSA에서 가장 먼저 부딪힌 문제는 "각 서비스가 어떻게 JWT를 검증할 것인가"였다.

### 고민: 비밀키 공유 vs 공개키 배포

**방법 A**: 모든 서비스에 JWT 비밀키를 공유 → 어떤 서비스가 뚫리면 전체 인증 체계가 무너진다
**방법 B**: auth-service만 비밀키를 보유하고, 다른 서비스는 공개키로 검증

**결론**: JWKS(JSON Web Key Set) 표준을 채택했다.

```
auth-service: RSA 키페어 생성 → /.well-known/jwks.json 으로 공개키 노출
gateway: 공개키로 JWT 서명 검증 → 사용자 정보를 헤더에 담아 전달
각 서비스: 헤더에서 사용자 정보 추출 (JWT 직접 검증 불필요)
```

이 구조의 장점은 auth-service가 일시적으로 다운되어도, 이미 발급된 JWT는 공개키로 검증 가능하다는 것이다. 서비스 간 비밀키 동기화 문제도 원천적으로 없다.

### 쿠키 기반 JWT

JWT를 HttpOnly + Secure 쿠키에 저장하는 방식을 선택했다. localStorage에 토큰을 저장하면 XSS 공격으로 탈취 가능하지만, HttpOnly 쿠키는 JavaScript에서 접근 자체가 불가능하다. 프론트엔드의 인증 흐름 설계와 맞물려 `SameSite`, `Secure` 속성까지 환경별로 제어할 수 있도록 환경변수화했다.

### 서비스간 인증: X-Gateway-Secret

서비스 간 내부 통신에는 별도의 `X-Gateway-Secret` 헤더를 사용한다. Gateway를 거치지 않는 직접 호출에서 "이 요청이 진짜 내부 서비스에서 온 것인가"를 검증하기 위한 장치다.

## 3. Gateway 설계 — "모든 트래픽의 관문"

### Spring Cloud Gateway (WebFlux)

Gateway는 다른 서비스와 달리 리액티브(WebFlux) 기반이다. 동기 서블릿 모델로는 다수의 동시 요청을 처리할 때 스레드 풀이 금방 고갈되기 때문이다. 리액티브 모델은 적은 스레드로 많은 동시 연결을 처리할 수 있어 Gateway에 적합했다.

### Gateway가 담당하는 것들

- JWT 검증 및 사용자 정보 헤더 주입
- 서비스별 라우팅 (`/auth/**` → auth-service, `/video/**` → video-service)
- CORS 처리 (전 서비스 통합)
- SSE 타임아웃 설정 (notification-service long-lived 커넥션 대응)
- 에러 응답 포맷 통일 (`GlobalErrorWebExceptionHandler`)

### CORS 중앙 관리의 교훈

초기에는 각 서비스마다 CORS 설정이 있었다. Gateway에서도 CORS 헤더를 추가하고, 각 서비스에서도 추가하니 **CORS 헤더 중복** 문제가 발생했다. 브라우저는 `Access-Control-Allow-Origin` 헤더가 2개 있으면 CORS 에러로 처리한다. Gateway에서만 CORS를 처리하고 각 서비스에서는 제거하는 방향으로 통일했다.

## 4. file-service Go 마이그레이션 — "기술 스택 교체가 가능한 아키텍처"

### 전환 전 상황

Java/Spring Boot 기반 file-service는 단순한 파일 업로드/다운로드에 비해 메모리 사용량(~512MB)과 응답 시간이 과도했다. 프로필 이미지 조회 같은 단순 API에 200ms 이상 걸리는 경우도 있었다.

### 전환 결정

Go(Gin + GORM)로 전면 재작성했다. MSA 덕분에 다른 서비스에는 영향 없이, file-service만 독립적으로 기술 스택을 교체할 수 있었다.

### 결과
- API 응답 속도: **100배 개선** (200ms → 2ms)
- 메모리 사용량: 512MB → ~50MB
- Docker 이미지 크기: 300MB+ → ~20MB
- 빌드 시간: 1분+ → 5초

### AWS S3 → MinIO 전환

처음에는 AWS S3를 사용했지만, 개발 환경에서의 비용과 네트워크 지연이 부담이었다. MinIO(S3 호환 오브젝트 스토리지)를 self-hosted로 구축하고, Nginx `/files/` 경로로 프록시하여 파일을 서빙한다. S3 호환 API를 사용하므로 추후 AWS S3로 전환할 때 코드 변경이 최소화된다.

## 5. email-service — "마이그레이션의 함정"

### AWS SES → Gmail SMTP OAuth2

초기에는 AWS SES를 사용했지만, Gmail SMTP OAuth2로 전환했다. `GmailOAuth2TokenService`가 Refresh Token으로 Access Token을 동적 발급하고, XOAUTH2 메커니즘으로 SMTP 인증한다.

### 겪은 3중 장애

프로덕션에서 이메일이 전혀 발송되지 않았다. 원인을 추적하니 3개의 문제가 동시에 존재했다:

1. **Gmail Refresh Token 만료**: Google Cloud 앱이 "테스트" 모드여서 토큰이 7일 후 만료
2. **SMTP 호스트 `localhost`**: docker-compose 기본값이 AWS SES 시절의 `localhost`로 남아있음
3. **STARTTLS 미적용**: SMTP 설정이 `onmeet.mail.*`에 있어 Spring Boot `spring.mail.*` 자동 구성에 미인식

세 번째 문제가 가장 까다로웠다. `onmeet.mail.properties.mail.smtp.starttls.enable=true`로 설정했는데, Spring Boot의 `JavaMailSender` 자동 구성은 `spring.mail.*` prefix만 인식한다. 설정이 존재하지만 적용되지 않는 침묵의 실패(silent failure)였다.

**교훈**: Spring Boot 자동 구성을 사용할 때는 반드시 공식 프로퍼티 prefix를 따라야 한다. 커스텀 prefix로 바꾸면 설정이 존재하지만 무시되는 위험한 상태가 된다.

## 6. 인프라 & CI/CD — "코드 밖의 코드"

### CI/CD 파이프라인

7개 서비스를 매번 전부 빌드하면 시간이 낭비된다. "변경된 서비스만 감지해서 빌드/배포"하는 파이프라인을 설계했다.

```
push to release/* 브랜치
  → dorny/paths-filter로 변경된 서비스 감지
  → .last_deployed_sha 파일로 마지막 배포 커밋 비교
  → 변경된 서비스만 Jib/Docker 빌드
  → Docker Hub push
  → GCP VM SSH 접속 → docker compose pull → 서비스 재시작
```

**Jib**을 선택한 이유: Dockerfile 없이 Gradle 플러그인만으로 Docker 이미지를 빌드한다. 레이어 캐싱이 기본 내장이라 의존성이 바뀌지 않으면 애플리케이션 코드 레이어만 다시 빌드한다.

### Nginx 설계

- `api.onmeet.cloud` → Gateway(8080) 프록시
- `rtc.onmeet.cloud` → LiveKit(7880) 프록시 (WebSocket 업그레이드 지원)
- `/files/` → MinIO(9000) 프록시 (읽기 전용)
- Let's Encrypt SSL 자동 갱신 (Certbot)

### Docker Compose 멀티파일 구조

각 서비스가 자체 `docker-compose.yml`을 가지고, 루트 `docker-compose.yml`이 `include`로 통합한다. 서비스별로 리소스 제한(CPU, 메모리), 헬스체크, 네트워크를 독립적으로 관리할 수 있다.

### 17회 릴리즈를 통해 배운 것

11주 동안 v0.1.0부터 v0.4.12까지 17회 릴리즈를 수행했다. 이 과정에서 파이프라인에 계속 개선 사항이 추가되었다:
- `LAST_DEPLOYED_SHA` 기반 변경 감지 (GitHub Variables → 서버 파일 기반으로 전환)
- Gateway 재배포 시 Nginx DNS 캐시 자동 갱신 (502 장애 재발 방지)
- 환경변수 자동 주입 (LIVEKIT, Firebase, Gmail OAuth2 등)

## 7. 응답 포맷 통일 — "약속된 계약이 중요하다"

### 문제

7개 서비스가 제각각 다른 응답 구조를 반환하고 있었다. 프론트엔드에서 서비스마다 파싱 로직을 다르게 구현해야 했고, 에러 응답 포맷도 제각각이었다.

### 해결

`onmeet-common` 모듈에 `ApiResponseWrappingAdvice` (ResponseBodyAdvice)를 구현했다. 모든 서비스의 응답을 자동으로 `{ success: true, data: T }` 형태로 래핑한다. AutoConfiguration으로 전 서비스에 자동 적용되며, JWKS 엔드포인트만 예외 처리했다.

```json
// 성공
{ "success": true, "data": { "id": 1, "name": "홍길동" } }

// 실패
{ "success": false, "error": { "code": "AUTH_001", "message": "인증이 필요합니다" } }
```

에러 처리도 `BusinessException` + 서비스별 `ErrorCode` enum으로 통일했다. `AuthErrorCode`, `VideoErrorCode`, `EmailErrorCode` 등 각 서비스가 자신의 에러 코드를 정의하고, 공통 `BaseGlobalExceptionHandler`가 처리한다.

## 8. 공통 모듈 설계 — "중복을 줄이되, 결합을 만들지 않기"

### onmeet-common

전 서비스가 공유하는 코드: `BusinessException`, `ErrorCode`, `ApiResponse`, `ApiResponseWrappingAdvice`

### common-security

보안 관련 공통 코드: `GatewayPreAuthFilter`, `BaseGlobalExceptionHandler`, `RemoteTeamSecurity`

### 설계 원칙

공통 모듈에 넣을지 말지의 기준은 "이 코드가 변경되면 모든 서비스를 재배포해야 하는가?"였다. 변경 빈도가 낮고 모든 서비스에서 동일하게 동작해야 하는 것만 공통 모듈에 넣었다. 서비스별로 다르게 동작할 수 있는 것(예: NotificationType)은 각 서비스에 두었다.

## 9. 이벤트 드리븐 아키텍처 — "서비스 간 결합도를 낮추다"

### Kafka를 선택한 이유

서비스 간 통신에 REST만 사용하면 강한 결합이 생긴다. video-service가 notification-service를 직접 호출하면, notification-service가 다운될 때 video-service까지 영향을 받는다.

Kafka를 이벤트 버스로 도입하여, 발행자는 구독자가 누구인지 알 필요 없이 토픽에 이벤트를 발행한다. 구독 서비스가 일시적으로 다운되어도 Kafka에 메시지가 보존되고 복구 후 소비한다.

### 주의점: 트랜잭션 순서

초대 생성에서 실제로 겪은 버그다. `sendInvitationEmail()` (Kafka 발행) → `invitationRepository.save()` (DB 저장) 순서로 구현했는데, DB 저장이 실패하면 이메일은 발송되었으나 초대 레코드가 없는 불일치가 발생한다. `save()` → Kafka 발행 순서로 변경하여 해결했다.

## 10. 장애 대응 — "CORS 에러가 진짜 CORS 문제가 아닐 때"

### 사례 1: 전체 서버 502 Bad Gateway

**증상**: `api.onmeet.cloud` 전체 502
**조사**: Nginx 에러 로그에서 `connect() failed (111: Connection refused)`
**원인**: Gateway 컨테이너 재시작 → Docker 내부 IP 변경 → Nginx가 이전 IP를 DNS 캐시로 보유
**해결**: `nginx -s reload`로 즉시 복구, CI/CD에 Gateway 배포 후 Nginx reload 자동화 추가
**교훈**: Nginx `proxy_pass`에 서비스명을 정적으로 쓰면 시작 시 1회만 DNS resolve한다

### 사례 2: 이메일 초대 미발송 (3중 장애)

**증상**: 기업 초대 이메일이 전송되지 않음
**원인**: Gmail Refresh Token 만료 + SMTP 호스트 localhost + STARTTLS 미적용이 동시에 겹침
**해결**: 토큰 재발급, docker-compose 기본값 수정, application.yml 설정 이동
**교훈**: 기술 스택 마이그레이션 시 설정 파일 전수 점검 필수. Spring Boot 자동 구성 prefix 혼용 주의.

### 사례 3: 한 서비스 장애가 전체로 전파

**증상**: notification API에 CORS error, file-service까지 CORS error
**원인**: notification-service DB 커넥션 풀 고갈 → 504 → Gateway 스레드 블로킹 → 전체 서비스 지연. 504 응답에 CORS 헤더가 없어 브라우저가 CORS error로 표시.
**해결**: 트랜잭션 분리로 DB 커넥션 점유 시간 최소화
**교훈**: **CORS 에러가 항상 CORS 문제는 아니다.** 백엔드 5xx에 CORS 헤더 누락 시 브라우저는 CORS error로 표시한다. 한 서비스 장애가 Gateway를 통해 전체에 전파될 수 있다.

### 사례 4: PR 병합 시 과거 코드 유입

**증상**: develop에서 `./gradlew build` 실패
**원인**: 오래된 feature 브랜치를 머지하면서 MSA 전환 전 모놀리식 코드 96개 파일이 유입
**해결**: git 이력 추적으로 유입 경로 특정, 96개 파일 삭제, 테스트 코드 현행화
**교훈**: 오래된 브랜치 머지 시 `git diff` 리뷰 필수. CI 전체 빌드 필수 체크 설정으로 사전 차단.

## 11. 돌아보며

이 프로젝트에서 가장 크게 성장한 부분은 **"장애를 통해 아키텍처의 의미를 체감한 것"**이다.

교과서에서 "서비스 간 장애 격리"를 읽었을 때는 막연했다. 하지만 한 서비스의 DB 커넥션 풀 고갈이 Gateway를 통해 전혀 다른 서비스까지 연쇄 장애를 일으키는 것을 직접 경험하고 나서야, "왜 서비스 간 타임아웃이 중요한지", "왜 Circuit Breaker가 필요한지"를 진짜로 이해하게 되었다.

또한 **"설정 하나가 전체 시스템을 멈출 수 있다"**는 것도 배웠다. `SPRING_MAIL_HOST=localhost` 한 줄이 이메일 서비스 전체를 먹통으로 만들었고, Nginx DNS 캐시 하나가 API 전체를 502로 만들었다. 코드뿐 아니라 설정 파일, 환경변수, 인프라 구성까지 "배포 가능한 코드"의 범위에 포함된다는 것을 체감했다.

11주, 510건의 커밋, 17회의 릴리즈. 숫자보다 중요한 것은 각 커밋마다 "왜 이렇게 했는가"에 대한 답을 가지고 있다는 것이다.
