## 슬라이드 9 — auth-service

> auth-service · Kotlin · Spring Security · AES-256-GCM + RS256

auth-service의 핵심은 **"서명용 개인키를 어떻게 안전하게 보관할 것인가"**입니다.

사용자가 로그인하면 JWT를 발급하는데, 위조를 막기 위해 **RSA-2048 개인키로 서명**합니다. 이 개인키를 **AES-256-GCM**으로 한 번 더 암호화해서 저장하며, AES 키는 비밀번호에서 **PBKDF2(반복 60만 회)**로 파생합니다. 브루트포스 공격을 현실적으로 불가능하게 만드는 구조입니다.

**JwtTokenProvider**에서 개인키를 복호화한 뒤 **RS256**으로 JWT를 서명하고, 다른 서비스는 `/.well-known/jwks.json` **JWKS 엔드포인트**의 공개키로 토큰을 검증합니다. **개인키는 auth-service 밖으로 절대 나가지 않으므로**, 한 서비스가 뚫려도 인증 체계 전체가 무너지지 않습니다.

**Refresh Token**은 Redis에 저장하고 **Rotation** 방식을 적용합니다. 사용할 때마다 새 토큰으로 교체하고 이전 토큰을 즉시 무효화하여, 탈취 시 정상 사용자의 갱신 실패로 탈취를 감지할 수 있습니다.

## 슬라이드 10 — gateway-service

> gateway-service · Kotlin · Spring Cloud Gateway · WebFlux

Gateway는 **모든 외부 요청이 반드시 거쳐야 하는 단일 진입점**입니다. 3개의 핵심 필터가 순서대로 동작합니다.

**CookieServerAuthenticationConverter** — JWT를 **HttpOnly 쿠키**에 저장해 XSS 토큰 탈취를 차단합니다. Spring Security는 기본적으로 Bearer 헤더에서 토큰을 찾으므로, 이 Converter가 쿠키에서 토큰을 꺼내 Bearer Token 형식으로 변환합니다.

**UserHeaderFilter** — JWT 검증 통과 후 사용자 정보(userId, email, roles)를 `X-User-Id`, `X-User-Email`, `X-User-Roles` 헤더에 주입합니다. Gateway가 한 번만 검증하므로 **뒷단 서비스는 JWT 라이브러리 자체가 불필요**합니다.

**SecureInternalFilter** — Gateway를 우회한 직접 요청으로 헤더를 위조하는 것을 막기 위해, 모든 요청에 **X-Gateway-Secret** 비밀 헤더를 추가합니다. 내부 서비스는 이 헤더가 있는 요청만 신뢰합니다.

전체 흐름:
`Browser Cookie → CookieConverter → NimbusJwtDecoder(JWKS 검증) → UserHeaderFilter → SecureInternalFilter → 뒷단 서비스`

## 슬라이드 14 — file-service

> file-service · Go · Gin · GORM · PostgreSQL · MinIO (S3) · AWS SDK v2

file-service는 파일 업로드/다운로드를 담당합니다. **보안**과 **성능** 두 가지를 동시에 잡아야 합니다.

**보안** — MIME 스푸핑은 `http.DetectContentType()`으로 파일의 실제 바이너리를 판별하여 차단합니다. S3 Key 인젝션은 ownerType을 4가지 whitelist로 제한하고, ownerId는 숫자만 허용하는 정규식으로 검증합니다. Path Traversal은 `../`나 `/` 포함 여부를 명시적으로 체크합니다.

**성능(Go 전환)** — Java/Spring Boot에서 Go(Gin + GORM)로 전면 재작성했습니다. goroutine 기반 경량 동시성, Semaphore 업로드 제한(채널 크기 10), 파일 크기별 스마트 캐싱(1MB 기준)을 적용한 결과:
- 응답 속도: **~450ms → ~4ms** (100배 이상 개선)
- 메모리: **~512MB → ~30MB** (17배 절감)

## 슬라이드 15 — email-service

> email-service · Java · Spring Boot · Thymeleaf · Gmail SMTP OAuth2

email-service는 기업 초대, 게스트 초대, 임시 비밀번호 등의 이메일을 발송합니다.

**Template 보안** — templateName을 외부에서 받으므로 Path Traversal 위험이 있습니다. **ALLOWED_TEMPLATES** Set으로 허용된 3가지 템플릿만 whitelist 방어합니다. "이것만 허용"이 "이것만 차단"보다 안전합니다.

**OAuth2 토큰 캐시** — Gmail SMTP의 OAuth2 토큰을 메모리에 캐시하고, **double-checked locking** 패턴으로 동시 갱신 요청을 방지합니다. TTL은 Google 만료 시간(60분)보다 5분 짧은 **55분**으로 설정해 레이스 컨디션을 방지합니다.

## 1. MSA & Gateway (hover: MSA & Gateway 브랜치)

프로젝트 초기에 모놀리식으로 시작했지만, video-service의 LiveKit 의존성이 빌드를 느리게 만들고, ai-service의 STT 처리가 다른 서비스에 영향을 주면서 **1주차에 MSA로 전환**했습니다. 7개 서비스를 도메인 경계로 분리하고, Kafka 이벤트 버스로 결합도를 낮췄습니다.

Gateway를 단일 진입점으로 두고 JWT 검증, 사용자 헤더 주입, 내부 인증을 중앙 처리했습니다. MSA 덕분에 file-service를 Java에서 Go로 독립 전환해 **응답 100배 개선**이라는 결과를 얻었습니다.

**아쉬운점** — **Circuit Breaker를 적용하지 못했습니다.** notification-service DB 커넥션 풀 고갈이 504를 발생시키고, CORS 에러로 전파되는 장애를 겪었습니다. Resilience4j로 장애 서비스를 자동 차단했다면 전체 장애 전파를 막을 수 있었을 것입니다. Rate Limiting도 미구현이어서 과도한 요청에 무방비 상태였고, 에러 응답에 CORS 헤더가 누락되어 "CORS 에러가 진짜 CORS 문제가 아닌" 상황에서 디버깅에 시간을 낭비했습니다.

---

## 2. 인증 & 보안 (hover: 인증 & 보안 브랜치)

JWKS 표준을 채택해 auth-service만 RSA 개인키를 보유하고, 공개키로 분산 검증하는 구조를 설계했습니다. HttpOnly 쿠키로 XSS 탈취를 원천 차단하고, file-service와 email-service에도 MIME 스푸핑 방어, Path Traversal 차단, whitelist 검증을 적용했습니다.

**아쉬운점** — **키 로테이션을 구현하지 못했습니다.** RSA 키 페어가 서버 재시작 전까지 고정되어, 실 프로덕션 기준으로는 보안 취약점입니다. 또한 JWT가 stateless라 발급 후 강제 무효화가 불가능한데, 토큰 블랙리스트를 구현하지 못해 비밀번호 변경이나 계정 탈취 시 즉시 세션을 끊을 수 없었습니다. 파일 업로드에서 MIME 검증은 했지만, 파일 내용 자체의 악성코드 스캔까지는 적용하지 못했습니다.

## 3. CI/CD (hover: CI/CD 브랜치)

변경된 서비스만 감지해서 빌드/배포하는 파이프라인을 설계하고, Jib 레이어 캐싱으로 빌드 속도를 최적화했습니다. 11주 동안 17회 릴리즈, 510건의 커밋을 수행했습니다.

**아쉬운점** — **인프라 레벨 문제를 사전에 예상하지 못했습니다.** Gateway 컨테이너 재시작 시 Nginx DNS 캐시가 이전 IP를 물고 있어 전체 API가 502로 멈추는 장애를 겪었습니다. email-service에서는 `spring.mail.*`과 커스텀 prefix `onmeet.mail.*`의 차이를 인지하지 못해 3중 장애가 발생했는데, CI 단계에서 설정 적용 여부를 검증하는 통합 테스트가 있었다면 막을 수 있었습니다. Go 전환 시에도 성능에 집중하느라 보안 검증 로직의 엣지 케이스 테스트를 충분히 작성하지 못했습니다.

## 4. AI 활용 개발 (hover: AI 활용 브랜치)

**장점** — 보일러플레이트, CRUD, DTO 매핑 같은 반복 작업을 AI에 위임해서 핵심 설계에 집중할 수 있었습니다. Go 전환 시 새로운 언어의 관용적 패턴을 빠르게 습득하고, 보안 취약점 패턴 검토, JWKS·PBKDF2 등 기술 조사 시간을 크게 단축했습니다.

**단점** — AI가 생성한 코드를 **"왜 이렇게 동작하는지" 이해하지 못한 채 넘어간 부분**이 있었습니다. email-service의 Spring Boot 자동 구성 이슈가 대표적입니다. AI가 제안한 설정을 그대로 적용했지만 prefix 차이를 인지하지 못해 장애로 이어졌습니다. 또한 에러 발생 시 직접 분석하기 전에 AI에게 먼저 물어보는 습관이 생겨, CORS 장애 때 네트워크 흐름을 직접 추적하는 대신 표면적 에러에 의존한 것이 아쉽습니다. Go를 빠르게 도입할 수 있었지만, goroutine 스케줄링이나 채널의 내부 동작 같은 깊은 이해 없이 패턴만 가져다 쓴 부분도 있습니다.

## 5. 전체 회고 (hover: 전체 회고 브랜치)

이 프로젝트에서 가장 크게 성장한 부분은 **장애를 통해 아키텍처의 의미를 체감한 것**입니다.

교과서에서 "서비스 간 장애 격리"를 읽었을 때는 막연했지만, DB 커넥션 풀 고갈이 전혀 다른 서비스까지 연쇄 장애를 일으키는 것을 직접 경험하고 나서야, "왜 서비스 간 타임아웃이 중요한지"를 진짜로 이해하게 되었습니다.

돌이켜보면 **"동작하는 코드"에 집중한 나머지 "운영 가능한 코드"에는 부족했다**고 느낍니다. Circuit Breaker, Rate Limiting, 발송 재시도 같은 회복탄력성 패턴을 초기 설계에 포함시켰다면 장애 대응이 훨씬 수월했을 것입니다.

AI 도구 활용은 양날의 검이었습니다. 11주라는 짧은 기간에 7개 서비스를 구축할 수 있었던 것은 AI의 도움이 컸지만, **"이해 없는 구현"이 장애로 이어지는 경험**을 통해 AI는 도구일 뿐 판단은 개발자의 몫이라는 것을 배웠습니다.

다음 프로젝트에서는 코드뿐 아니라 설정, 환경변수, 인프라까지 **"배포 가능한 코드"의 범위를 확장**하고, AI를 활용하되 **핵심 동작 원리는 반드시 직접 이해한 뒤 적용**하는 원칙을 지키겠습니다.
