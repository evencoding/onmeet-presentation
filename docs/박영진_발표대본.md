## 1. auth-service (슬라이드 9) — hover: 인증 브랜치

> auth-service · Kotlin · Spring Security · AES-256-GCM + RS256

### 기술 설명

auth-service의 핵심은 **"서명용 개인키를 어떻게 안전하게 보관할 것인가"**입니다.

먼저 배경을 설명드리면, 우리 서비스는 사용자가 로그인하면 **JWT(JSON Web Token)**라는 토큰을 발급합니다. JWT는 쉽게 말해 "이 사람이 누구인지" 적혀 있는 디지털 신분증인데, 위조를 막기 위해 **서버만 가진 개인키로 서명**을 합니다. 문제는 이 개인키가 유출되면 누구든 가짜 토큰을 만들 수 있다는 것입니다.

**KeyManager.kt**에서는 RSA-2048이라는 알고리즘으로 키 페어를 생성합니다. RSA는 공개키와 개인키 한 쌍을 만드는데, 개인키로 서명하고 공개키로 검증하는 구조입니다. 이 개인키를 그냥 파일로 저장하면 서버가 해킹됐을 때 바로 탈취됩니다. 그래서 개인키 자체를 다시 **AES-256-GCM**이라는 대칭키 암호화로 한 번 더 암호화해서 저장합니다.

여기서 AES 암호화에 쓸 키는 어디서 오느냐? 비밀번호에서 파생합니다. **PBKDF2**라는 키 파생 함수가 비밀번호를 받아서 암호화 키를 만들어주는데, 이때 **반복 횟수를 60만 회**로 설정했습니다. 해커가 비밀번호를 하나하나 대입하는 브루트포스 공격을 하면, 한 번 시도할 때마다 60만 번의 해시 연산을 해야 하니 현실적으로 불가능해집니다. 저장 포맷은 `Salt(16바이트) + IV(12바이트) + CipherText` 순서로 이어붙여서, 나중에 복호화할 때 Salt와 IV를 분리해서 쓸 수 있게 합니다.

**JwtTokenProvider.kt**에서는 이렇게 보호된 개인키를 복호화한 뒤, **RS256** 알고리즘으로 JWT를 서명합니다. 토큰 안에는 userId, email, roles 같은 사용자 정보가 들어가고, 유효기간은 30분입니다.

그러면 다른 서비스들은 이 토큰이 진짜인지 어떻게 확인할까요? auth-service가 `/.well-known/jwks.json`이라는 **JWKS 엔드포인트**로 공개키를 노출합니다. JWKS는 "JSON Web Key Set"의 약자로, 공개키를 표준 JSON 형식으로 제공하는 규격입니다. Gateway가 이 공개키를 가져다가 토큰 서명을 검증합니다. 핵심은 **개인키는 auth-service 밖으로 절대 나가지 않는다**는 것입니다. 다른 서비스에 비밀키를 공유할 필요가 없으니 한 서비스가 뚫려도 인증 체계 전체가 무너지지 않습니다.

**Refresh Token**은 왜 필요할까요? accessToken의 유효기간이 30분이니, 30분마다 다시 로그인하면 사용자 경험이 나빠집니다. 그래서 유효기간이 긴(7일) Refresh Token을 별도로 발급하고, accessToken이 만료되면 Refresh Token으로 새 accessToken을 발급받습니다. Refresh Token은 **Redis**(인메모리 DB)에 저장하고, **Rotation** 방식을 적용합니다. Rotation이란 Refresh Token을 사용할 때마다 새 토큰으로 교체하고 이전 토큰을 즉시 무효화하는 것입니다. 만약 해커가 Refresh Token을 탈취해서 사용하면, 정상 사용자의 다음 갱신이 실패하므로 탈취 사실을 감지할 수 있습니다.

### 회고

인증 아키텍처를 설계하면서 **"보안은 설계 단계에서 결정된다"**는 것을 체감했습니다. 비밀키 공유 방식을 선택했다면 이후에 아무리 코드를 잘 작성해도 구조적 취약점을 해결할 수 없었을 것입니다. JWKS라는 표준을 채택한 덕분에 서비스 간 비밀키 동기화 문제가 원천적으로 사라졌고, 인증의 단일 장애점도 제거할 수 있었습니다.

## 2. gateway-service (슬라이드 10) — hover: Gateway 브랜치

> gateway-service · Kotlin · Spring Cloud Gateway · WebFlux

### 기술 설명

Gateway는 **모든 외부 요청이 반드시 거쳐야 하는 단일 진입점**입니다. 건물에 비유하면 정문 경비실과 같습니다. 누가 왔는지 신분증(JWT)을 확인하고, 어디로 가야 하는지 안내하고, 내부 직원임을 증명하는 출입증(헤더)을 달아주는 역할입니다.

이 Gateway는 3개의 핵심 필터가 순서대로 동작합니다.

**첫째, CookieServerAuthenticationConverter** — 이것을 이해하려면 먼저 "왜 쿠키를 쓰는가"를 알아야 합니다. JWT를 브라우저에 저장하는 방법은 크게 두 가지입니다. localStorage에 넣거나, 쿠키에 넣거나. localStorage에 넣으면 JavaScript로 쉽게 꺼낼 수 있는데, 이게 문제입니다. XSS(Cross-Site Scripting) 공격으로 악성 스크립트가 주입되면 토큰이 그대로 탈취됩니다. 반면 **HttpOnly 쿠키**는 JavaScript에서 접근 자체가 불가능합니다. 브라우저가 자동으로 요청에 붙여주기만 하고, 코드로는 읽을 수 없습니다. 그런데 Spring Security의 JWT 검증 로직은 기본적으로 `Authorization: Bearer xxx` 헤더에서 토큰을 찾습니다. 쿠키에서는 안 찾아요. 그래서 이 Converter가 **쿠키에서 토큰을 꺼내 → Spring Security가 이해하는 Bearer Token 형식으로 변환**해주는 다리 역할을 합니다.

**둘째, UserHeaderFilter** — JWT 검증이 통과하면, 토큰 안에 들어있는 사용자 정보(userId, email, roles)를 꺼내서 **HTTP 헤더에 주입**합니다. `X-User-Id`, `X-User-Email`, `X-User-Roles`라는 헤더를 만들어서 뒷단 서비스에 전달합니다. 왜 이렇게 하냐면, 뒷단의 7개 서비스가 각각 JWT를 검증하면 모든 서비스가 JWKS 공개키를 가져와야 하고, 검증 로직도 중복됩니다. Gateway가 한 번만 검증하고 결과를 헤더로 전달하면, **뒷단 서비스는 JWT 라이브러리 자체가 필요 없습니다**. 헤더에서 userId만 꺼내면 됩니다.

**셋째, SecureInternalFilter** — 그런데 문제가 하나 있습니다. 누군가 Gateway를 거치지 않고 뒷단 서비스에 직접 요청을 보내면서 `X-User-Id: 1` 같은 헤더를 위조하면 어떻게 될까요? 뒷단 서비스는 이게 Gateway가 넣어준 건지, 해커가 위조한 건지 구분할 수 없습니다. 이것을 막기 위해 Gateway가 모든 요청에 **X-Gateway-Secret**이라는 비밀 헤더를 추가합니다. 이 값은 Gateway와 내부 서비스만 알고 있는 비밀키입니다. 내부 서비스는 이 헤더가 있는 요청만 신뢰합니다.

전체 흐름을 정리하면 이렇습니다:
`Browser Cookie → CookieConverter(쿠키→Bearer 변환) → NimbusJwtDecoder(JWKS로 서명 검증) → UserHeaderFilter(사용자 정보 헤더 주입) → SecureInternalFilter(내부 인증 헤더 추가) → 뒷단 서비스`

### 회고

Gateway에서 가장 인상적이었던 장애는 **"CORS 에러가 진짜 CORS 문제가 아닐 때"**입니다. notification-service의 DB 커넥션 풀이 고갈되면서 504 응답이 발생했는데, 504에 CORS 헤더가 없어서 브라우저가 CORS error로 표시했습니다. **한 서비스의 장애가 Gateway를 통해 전체로 전파될 수 있다**는 것을 직접 경험했고, 서비스 간 타임아웃과 Circuit Breaker의 필요성을 진짜로 이해하게 된 계기였습니다.

## 3. file-service (슬라이드 14) — hover: Go 전환 브랜치

> file-service · Go · Gin · GORM · PostgreSQL · MinIO (S3) · AWS SDK v2

### 기술 설명

file-service는 프로필 이미지, 회의 첨부파일 같은 **파일 업로드/다운로드를 담당하는 서비스**입니다. 파일 서버는 단순해 보이지만, 보안과 성능 두 가지를 동시에 잡아야 합니다.

**보안 — 왜 파일 업로드가 위험한가?**

파일 업로드는 서버 보안에서 가장 위험한 기능 중 하나입니다. 세 가지 공격을 방어해야 합니다.

첫째, **MIME 스푸핑**입니다. 해커가 악성 스크립트를 `image.jpg`라는 이름으로 업로드할 수 있습니다. 파일 확장자만 보면 이미지처럼 보이지만, 실제 내용은 스크립트입니다. 이것을 방어하기 위해 `http.DetectContentType()`으로 **파일의 실제 바이너리(첫 512바이트)**를 읽어서 진짜 파일 타입을 판별합니다. 확장자가 jpg여도 내용이 이미지가 아니면 거부합니다.

둘째, **S3 Key 인젝션**입니다. 파일을 S3(클라우드 저장소)에 저장할 때 경로가 `USER/123/profile.jpg` 같은 형태인데, 만약 ownerType에 `../../admin` 같은 값을 넣으면 다른 사용자의 파일에 접근할 수 있습니다. 이것을 막기 위해 ownerType은 `USER/TEAM/COMPANY/MEETING` **네 가지만 허용하는 whitelist**로 제한하고, ownerId는 **숫자만 허용하는 정규식**으로 검증합니다.

셋째, **Path Traversal**입니다. 파일 경로에 `../`를 넣어서 서버의 상위 디렉토리에 접근하는 공격입니다. 이것은 `../`나 `/` 포함 여부를 명시적으로 체크하여 차단합니다.

**성능 — 왜 Go인가?**

원래 Java/Spring Boot로 만들었는데, 단순한 파일 전달에 JVM이 메모리를 512MB나 먹고 응답도 450ms 걸렸습니다. Go는 컴파일 언어라 JVM 같은 런타임 오버헤드가 없고, **goroutine**이라는 경량 스레드로 동시성을 처리합니다. Java의 Thread는 하나에 약 1MB 메모리를 쓰지만, goroutine은 약 2KB만 씁니다.

**Semaphore 업로드 제한**은 Go의 채널(`chan struct{}{}`)로 구현했습니다. 채널 크기를 10으로 설정하면, 동시에 10개까지만 업로드 goroutine이 실행됩니다. 11번째 요청이 오면 채널에 빈 자리가 생길 때까지 자동으로 대기합니다. 서버 리소스가 폭주하는 것을 막는 안전장치입니다.

**스마트 캐싱**은 파일 크기에 따라 전략을 나눕니다. 프로필 이미지처럼 작은 파일(1MB 미만)은 메모리에 캐시해서 빠르게 응답하고, 큰 파일(1MB 이상)은 메모리를 낭비하지 않도록 S3에서 직접 스트리밍합니다.

전환 결과:
- 응답 속도: **Kotlin ~450ms → Go ~4ms** (100배 이상 개선)
- 메모리: **JVM ~512MB → Go ~30MB** (17배 절감)
- 동시성: **Thread pool (고정 크기) → goroutines (수만 개 가능)**

### 회고

이 전환은 **MSA의 진짜 장점을 체감한 순간**이었습니다. 모놀리식이었다면 기술 스택 교체는 불가능했을 것입니다. MSA 덕분에 다른 서비스에 영향 없이 file-service만 독립적으로 Java에서 Go로 교체할 수 있었습니다. "서비스별로 최적의 기술을 선택할 수 있다"는 MSA의 교과서적 장점을, 직접 100배의 성능 개선이라는 수치로 증명한 사례였습니다.

## 4. email-service (슬라이드 15) — hover: 이메일 브랜치

> email-service · Java · Spring Boot · Thymeleaf · Gmail SMTP OAuth2

### 기술 설명

email-service는 기업 초대, 게스트 초대, 임시 비밀번호 같은 **이메일을 발송하는 서비스**입니다. 핵심은 두 가지입니다 — 템플릿 보안과 토큰 관리.

**Template 보안 — 왜 이메일 템플릿이 위험한가?**

이메일 본문은 **Thymeleaf**라는 템플릿 엔진으로 생성합니다. 예를 들어 `company-invitation`이라는 템플릿에 회사명, 초대 링크 같은 변수를 채워서 HTML 이메일을 만듭니다. 문제는 templateName을 외부에서 받는다는 것입니다. 만약 templateName에 `../../etc/passwd` 같은 값을 넣으면, 서버의 시스템 파일을 읽어서 이메일로 보내는 **Path Traversal 공격**이 가능해집니다.

이것을 막기 위해 **ALLOWED_TEMPLATES**라는 Set(집합)을 만들어, `company-invitation`, `guest-invitation`, `temporary-password` **세 가지 이름만 허용**합니다. 이 세 가지가 아닌 다른 templateName이 들어오면 즉시 예외를 발생시킵니다. 이 방식을 **whitelist 방어**라고 합니다. "이것만 허용"이 "이것만 차단"보다 안전합니다. 새로운 공격 패턴이 나와도 whitelist에 없으면 자동으로 차단되기 때문입니다.

**OAuth2 토큰 캐시 — 왜 매번 발급받으면 안 되는가?**

이메일 발송에는 Gmail SMTP를 사용하는데, Gmail은 OAuth2 인증을 요구합니다. 이메일을 보낼 때마다 Google 서버에 Access Token을 요청하면, 네트워크 왕복 시간이 추가되고 Google의 Rate Limit에도 걸릴 수 있습니다.

**GmailOAuth2TokenService.java**에서는 한 번 발급받은 토큰을 **메모리에 캐시**합니다. 다음 요청이 오면 캐시된 토큰이 아직 유효한지 확인하고, 유효하면 Google에 요청하지 않고 바로 반환합니다.

여기서 기술적으로 중요한 부분이 **double-checked locking** 패턴입니다. 웹 서버는 여러 요청을 동시에 처리합니다. 만약 두 요청이 동시에 "토큰이 만료됐네, 새로 발급받자"를 실행하면, Google에 불필요한 중복 요청이 갑니다. 이것을 막기 위해 `volatile` 키워드로 토큰 변수를 선언하고(모든 스레드가 최신 값을 보도록), `synchronized`로 갱신 로직을 감쌉니다(한 번에 하나의 스레드만 실행하도록). 먼저 캐시를 확인하고(1차 체크), synchronized 블록에 들어간 뒤 다시 확인하고(2차 체크), 그래도 만료됐으면 그때 갱신합니다. 이게 "double-checked"인 이유입니다.

TTL은 **55분**으로 설정했습니다. Google Access Token의 실제 만료 시간은 60분인데, 딱 60분으로 맞추면 "토큰이 유효하다고 판단했는데 Google 서버에 도착하는 순간 만료되는" 타이밍 문제가 발생할 수 있습니다. 5분의 여유를 두면 이런 **레이스 컨디션(경합 상태)**을 방지합니다.

### 회고

프로덕션에서 이메일이 전혀 발송되지 않는 **3중 장애**가 동시에 발생했습니다 — Gmail Refresh Token 만료, SMTP 호스트 localhost 잔존, STARTTLS 미적용. 가장 까다로웠던 것은 Spring Boot의 `JavaMailSender` 자동 구성이 `spring.mail.*` prefix만 인식하는데, 커스텀 prefix인 `onmeet.mail.*`에 설정을 넣어서 **설정이 존재하지만 적용되지 않는 침묵의 실패(silent failure)**가 발생한 것이었습니다. 기술 스택 마이그레이션 시 코드뿐 아니라 **설정 파일, 환경변수, 인프라 구성까지 전수 점검이 필수**라는 교훈을 얻었습니다.

## 5. MSA 설계 (hover: MSA 설계 브랜치)

프로젝트 초기에 모놀리식으로 시작했지만, 1주차에 MSA로 전환하는 결정을 내렸습니다.

**전환 계기**는 video-service의 LiveKit 의존성이 auth-service의 빌드를 느리게 만들고, ai-service의 무거운 STT 처리가 다른 서비스 응답 시간에 영향을 주는 상황이었습니다.

7개 서비스를 도메인 경계로 분리하고, 서비스 간 통신은 Kafka 이벤트 버스로 결합도를 낮췄습니다. MSA 덕분에 **서비스별로 최적의 기술을 선택**할 수 있었고, file-service를 Java에서 Go로 전환한 것이 대표적인 사례입니다.

---

## 6. 인증 & Gateway (hover: 인증 & Gateway 브랜치)

MSA에서 가장 먼저 부딪힌 문제는 "각 서비스가 어떻게 JWT를 검증할 것인가"였습니다.

모든 서비스에 비밀키를 공유하면 한 서비스가 뚫렸을 때 전체가 무너집니다. 그래서 **JWKS 표준**을 채택했습니다. auth-service만 RSA 개인키를 보유하고, `/.well-known/jwks.json`으로 공개키를 노출합니다. Gateway가 공개키로 JWT를 검증하고 사용자 정보를 헤더에 담아 전달하는 구조입니다.

JWT는 **HttpOnly Secure 쿠키**에 저장해서 XSS 토큰 탈취를 원천 차단했고, CORS는 Gateway에서만 중앙 관리하여 헤더 중복 문제도 해결했습니다.

---

## 7. Go 전환 (hover: Go 전환 브랜치)

Java/Spring Boot 기반 file-service는 단순한 파일 업로드/다운로드에 **메모리 512MB, 응답 200ms**로 과도했습니다.

Go(Gin + GORM)로 전면 재작성한 결과:
- API 응답: **200ms → 2ms** (100배 개선)
- 메모리: **512MB → 50MB**
- Docker 이미지: **300MB → 20MB**

MSA 아키텍처 덕분에 다른 서비스에 영향 없이, file-service만 독립적으로 기술 스택을 교체할 수 있었습니다. 이것이 MSA의 진짜 장점이었습니다.

---

## 8. 장애 대응 (hover: 장애 대응 브랜치)

운영 중 겪은 세 가지 주요 장애가 있었습니다.

첫째, **Nginx DNS 캐시 502**. Gateway 컨테이너가 재시작되면서 Docker 내부 IP가 바뀌었는데, Nginx가 이전 IP를 캐시하고 있어서 전체 API가 502로 멈췄습니다. CI/CD에 Gateway 배포 후 Nginx reload를 자동화해서 해결했습니다.

둘째, **이메일 3중 장애**. Gmail Refresh Token 만료, SMTP 호스트가 localhost로 남아있던 것, STARTTLS가 Spring Boot 자동 구성에 미인식된 것이 동시에 겹쳤습니다. 기술 스택 마이그레이션 시 설정 파일 전수 점검이 필수라는 교훈을 얻었습니다.

셋째, 가장 인상적이었던 것은 **"CORS 에러가 진짜 CORS 문제가 아닐 때"**입니다. notification-service DB 커넥션 풀이 고갈되면서 504 응답이 발생했는데, 504에 CORS 헤더가 없어서 브라우저가 CORS error로 표시했습니다. 한 서비스의 장애가 Gateway를 통해 전체로 전파된 사례였습니다.

## 9. CI/CD & 인프라 (hover: CI/CD & 인프라 브랜치)

7개 서비스를 매번 전부 빌드하면 시간이 낭비됩니다. **변경된 서비스만 감지해서 빌드/배포**하는 파이프라인을 설계했습니다.
